# 星枢企业业务平台 NexusOne：技术框架 V1.1

> **文档状态**：基准版（V1.1 评审修订）  
> **日期**：2026-09-22  
> **定位**：V1.1 技术框架基准。  
> **目标**：在保证 P1–P5 产品边界、租户隔离、权限一致性、业务闭环和交付能力的前提下，控制基础设施组件、分布式复杂度、运维成本和私有化交付成本，并满足信创、等保和商用密码交付要求。  
> **范围外**：AI 由其他项目组负责，不进入本项目功能、排期、技术债和运行责任。

## 0. 技术原则

> **先把产品做成，再把平台做大。组件只有在明确解决已出现的问题时才引入，不为未来假设提前建设分布式基础设施。**

首期采用模块化单体。外部基础组件统一为关系数据库（PostgreSQL / GaussDB）、Redis、MinIO / AIStor、Keycloak；Flowable、Quartz、Flyway 作为应用内成熟组件使用。协议收敛为 HTTP/REST、JDBC、Redis Protocol、S3 API。项目组已确认 Keycloak、Flowable、Quartz、Flyway 可纳入国产化交付路线，V1.1 不再为这四项预设首期替代方案，只保留 Adapter/Port 边界并在 P0 锁定版本组合。

业务代码只依赖协议与 Port，不依赖任何组件的私有模型或产品名。

Kafka、OpenSearch、API Gateway、独立 Secret 平台和 Kubernetes 达到第 21 节触发条件后再评估引入。

## 1. 产品与技术边界

| 产品 | 产品名 | 核心技术责任 | 唯一真相源 |
|---|---|---|---|
| P1 | 星域·租户中心 Nexus Tenant | Tenant、租户关系、租户隔离、运行态权益、Quota、文件/通知/基础运维 | Tenant、Tenant Relation、Runtime Entitlement Projection |
| P2 | 星权·身份权限中心 Nexus IAM | Person、Department、Position、Role、Permission、DataScope、FieldPolicy | Identity、Organization、Permission |
| P3 | 星构 Nexus Studio | App、Schema、Ledger、Form、Workflow、Rule、View、Runtime、Task、Report | Business Metadata、Business Data |
| P4 | 星市 Nexus Market | Package、Version、Install/Upgrade、Product、SKU、Subscription、Commercial Entitlement | Product、SKU、Subscription、Commercial Entitlement |
| P5 | 星联 Nexus Connect | API、Webhook、Connector、Credential Reference、外部系统适配 | Integration Configuration |

领域规则：

- 一个 Tenant 对应一个法人根；
- 独立法人子公司默认独立 Tenant，集团关系通过 P1 租户关系图表达；
- 平台自身使用一个保留的平台租户（platform scope），平台管理员、平台配置和跨租户工具都归属该 scope；
- P2 是人员、组织、岗位和权限策略唯一真相源；
- P4 是商业权益唯一真相源；
- P1 只保存运行态权益投影；
- P3 必须拥有自己的 Schema / Ledger / Runtime；
- 本项目不包含数字人领域对象；
- 本项目不包含 AI 能力。

### 2.1 首期部署原则

业务平台首期采用：

> **模块化单体 + 少量独立基础服务**

不按 P1–P5 强制拆成五套微服务。

建议代码结构：

```text
nexusone
├─ nexus-bootstrap
├─ nexus-p1-tenant
├─ nexus-p2-iam
├─ nexus-p3-studio
├─ nexus-p4-market
├─ nexus-p5-connect
│
├─ nexus-permission-core
├─ nexus-data-core          <- Query Compiler / Tenant Guard / Ledger Storage
├─ nexus-expression-core    <- 受限表达式与沙箱
├─ nexus-event-core
├─ nexus-task-core          <- Quartz + Task Queue
├─ nexus-file-core
├─ nexus-notification-core
├─ nexus-audit-core
├─ nexus-crypto-core        <- CryptoPort / SecretPort
└─ nexus-common
```

产品边界通过 Java Module、Package、数据库访问边界和接口约束保持，而不是靠"每个产品一个微服务"维持。

### 3.1 框架级通用约定

- **ID**：主键使用 UUIDv7（时间有序），对外编码使用可读业务编码；不使用数据库自增作为对外 ID；
- **时间**：数据库统一存 UTC `timestamptz`，租户时区只用于展示与解析；
- **API**：`/api/v{n}/...` 版本前缀，向后兼容变更不升版本；错误响应统一 `code / message / trace_id / details`，错误码按 `产品.模块.编号` 编排；
- **i18n**：后端消息与前端文案统一资源键，首期简体中文、英文；
- **并发**：所有可编辑聚合带 `version` 乐观锁；
- **软删除**：`deleted_at`，查询默认过滤；
- **测试分层**：单元 → 契约测试（第 27 节）→ 场景集成 → 组合矩阵验收。

## 5. 部署架构

### 5.1 SaaS 部署

建议：

```text
Linux Servers
|
+-- Nginx
|
+-- NexusOne App Instance 1
+-- NexusOne App Instance 2
|
+-- Keycloak
|
+-- Redis
+-- PostgreSQL / GaussDB
+-- MinIO / AIStor
```

Flowable 引擎在 NexusOne 进程内，不单独占一台首期服务。

多实例通过 Nginx 负载均衡。

### 5.2 独立部署

推荐优先级：

1. Docker Compose；
2. systemd + Spring Boot executable JAR；
3. 客户已有容器平台时可适配，但 Kubernetes 不属于产品强依赖。

### 5.3 部署能力边界

以下能力由应用与基础组件自身提供，不依赖 Kubernetes API：

- Tenant 管理；
- Job 调度；
- Secret 读取；
- 服务发现；
- 健康检查；
- 配置管理；
- 文件存储；
- 日志；
- 备份；
- 升级；
- 回滚。

这样 SaaS 与独立部署仍可共用同一业务代码。

## 6. 信创、GaussDB-only 与合规基线

### 6.1 信创目标组合

以下组合在 P0 锁定并进入组合矩阵验收：

| 层 | 目标 | 验收口径 |
|---|---|---|
| 操作系统 | openEuler / 银河麒麟 / 统信 UOS 服务器版 | 全部组件可安装、可升级、可离线部署 |
| CPU 架构 | 鲲鹏 / 飞腾（ARM64）、海光（x86_64） | 与 5.2 部署方式组合验证 |
| JDK | OpenJDK 21 兼容发行版（含毕昇 JDK 等） | 应用与 Keycloak 均可运行 |
| 数据库 | GaussDB | 6.2 全部通过 |
| 缓存 / 对象存储 / Nginx | 不依赖数据库，只要求在上述 Linux + CPU 组合上运行 | 通过 RedisContractTest / ObjectStorageS3ContractTest / 入口验收；不要求国产发行版 |
| 浏览器 | Chromium 内核国产浏览器 + 主流浏览器 | H5 / Web 验收矩阵 |

### 6.2 国产化数据库组件基线

项目组已完成组件可行性调研，V1.1 将 **Keycloak、Flowable、Quartz、Flyway** 正式保留在国产化技术路线中，不再把它们列为“可能替换”的首期架构风险。

P0 的目标从“能不能用”调整为：

> **锁定确定版本组合，并完成 PostgreSQL / GaussDB、国产 Linux / CPU 环境下的安装、初始化、事务、锁、升级和回滚验收。**

| 组件 | V1.1 定位 | P0 必测 |
|---|---|---|
| Keycloak | 正式 IAM 引擎；P2 仍持有 Person/Org/Position/Role/Policy 主数据 | 建库、升级、登录、OIDC/SAML、Session、MFA、Organizations/Federation、备份恢复 |
| Flowable | 正式 BPMN/DMN 执行引擎；首期同进程、同库独立 Schema | 建表、事务、历史表、DMN、异步执行器、升级脚本、应用回滚兼容 |
| Quartz | 正式周期/定时调度库；不单独部署 | JDBC JobStore、Cluster、锁、Misfire、故障转移 |
| Flyway | 正式平台静态 Schema Migration 工具 | 版本表、事务迁移、Repeatable Script、升级、失败恢复 |
| Nexus Data Access | P1–P5 业务表统一访问层 | Query AST、Tenant/DataScope 注入、PostgreSQL/GaussDB Dialect、动态 DDL |
| P3 SchemaService | 动态台账 DDL 与 Schema 演进 | 表创建、字段扩展、Schema Drift、Forward-Compatible Migration |

边界保持：

- Keycloak、Flowable、Quartz 的内部表由组件自己访问，不接入 Nexus Query AST；
- Flyway 只管理平台静态表，不管理 P3 动态台账物理表；
- Nexus 自有业务代码不得绕过统一数据访问层直接执行原生 SQL；
- 组件升级仍必须跑各自 Contract Test。

### 6.3 商用密码（SM2 / SM3 / SM4）

密码能力统一经过 `CryptoPort`，提供两套算法套件，部署时选择，不允许同一密文混用两套：

| 能力 | 国际套件 | 商用密码套件 |
|---|---|---|
| 对称加密（敏感字段、Credential Envelope、导出包） | AES-256-GCM | SM4-GCM |
| 摘要 / 完整性（审计哈希链、文件 Checksum） | SHA-256 | SM3 |
| 签名（应用包签名、Webhook 签名、SPI 插件签名） | ECDSA / RSA | SM2 |
| 消息认证 | HMAC-SHA256 | HMAC-SM3 |
| 传输 | TLS 1.2/1.3 | GM/T 0024 国密 TLS，Nginx 双证书并行 |
| 口令哈希 | Keycloak 默认（PBKDF2 / Argon2） | Keycloak PasswordHashProvider SPI（PBKDF2-SM3），P0 评估工作量 |
| 密钥管理 | Master Key（16.1）/ KMS Adapter | 国密 KMS / 密码机 Adapter（SecretPort 可选实现） |

规则：

- 套件选择是部署级配置，记录在部署清单与审计中；
- 所有密文携带套件与密钥版本标识，支持轮换；
- 业务代码不得直接调用 JCE / Bouncy Castle，只调用 CryptoPort。

### 6.4 等保三级技术项映射

| 等保要求 | 平台落点 |
|---|---|
| 身份鉴别：双因子、口令复杂度、失败锁定、会话超时 | Keycloak 策略 + P2-M09；平台管理员强制 MFA |
| 访问控制：三权分立 | 平台侧系统管理员 / 安全管理员 / 审计管理员分离（P1-M05-G01-F003），审计管理员不可修改审计 |
| 安全审计：覆盖每个用户、留存 ≥ 6 个月、防篡改 | 审计热 90 天 + 归档 365 天；审计表 append-only，按批次 SM3/SHA-256 哈希链 |
| 剩余信息保护 | 租户注销后的保留期与最终销毁；缓存与临时文件带 TTL 与清理 Job |
| 通信完整性 / 保密性 | TLS / 国密 TLS；内部调用不走明文公网 |
| 数据完整性 / 保密性 | 敏感字段加密、FieldPolicy 脱敏、导出审计 |
| 个人信息保护（PIPL） | 最小采集、个人数据导出与删除接口、跨境不在首期范围 |
| 恶意代码 / 入侵防范 | 上传文件 MIME 与大小校验、表达式沙箱、CSP、白名单 IFrame |

## 7. 执行通道：Quartz / Task Queue / Outbox

平台只允许三条后台执行通道，业务 Job 不允许自行创建线程池和 Timer：

```text
Quartz            定时 / 周期任务（cron、固定间隔、延迟触发）
Task Queue        一次性异步作业（数据库任务表 + Worker，租约 + SKIP LOCKED）
Outbox Dispatcher 领域事件投递（第 15 节）
```

三条通道共用：

```text
Tenant Context（缺失即失败）
Job Lock / 租约
Idempotency（数据库幂等表）
Retry / Backoff
Job Log
Failure Handling / Dead Letter
```

### 7.1 Quartz

- 单实例：普通 Scheduler；
- 多实例：JDBC JobStore / Cluster Mode；
- 适用：配额重置、订阅到期处理、待办超期提醒、Reconciliation、审计归档、临时文件清理、备份任务协调、通知与 Webhook 重试的周期触发。

### 7.2 Task Queue

- 适用：异步大批量导入导出、报表生成、应用发布/安装事务的长步骤、数据模型迁移、租户导出/恢复；
- 任务表包含 tenant_id、type、payload、status、lease_until、attempt、last_error；
- Worker 数与并发上限按租户 Quota（任务并发量）限制。

### 7.3 Flowable 内部执行器

Flowable 异步执行器属于引擎自身，不受"不得自建线程池"约束，但必须与 Task Queue 共享同一租户上下文传播规则。

## 8. Redis 缓存路线

缓存统一使用 **Redis**。业务代码仍通过 CachePort / DistributedLockPort / CounterPort 隔离，不把 Redis 数据结构变成领域契约。

### 8.1 使用范围

只承担可丢失、可重建的状态：

- Cache；
- Token 撤销黑名单（丢失只导致强制下线延迟到 Token 到期）；
- 验证码；
- 临时 Token；
- 分布式锁（非资金、非不可逆操作）；
- Rate Limit Counter；
- UX 级防重复提交 Key；
- 热点配置；
- PolicySnapshot Cache。

### 8.2 不允许

不作为：

- 业务真相数据库；
- 审计持久化；
- Subscription 真相源；
- Workflow 历史库；
- 文件元数据真相源；
- **关键路径幂等键存储**（Outbox 消费、支付回调、安装/升级事务的幂等键落数据库幂等表）。

### 8.3 租户隔离

统一 Key 前缀：

```text
nexus:{env}:{tenant_id}:{module}:{key}
```

平台级数据使用明确的 `platform` scope。

### 8.4 封装

业务代码只依赖：

```text
CachePort
DistributedLockPort
CounterPort
```

不允许业务模块直接使用缓存私有数据结构作为领域契约。

## 9. MinIO / AIStor 对象存储路线

> **对象存储统一采用 MinIO / AIStor 产品线，业务层统一使用 S3 API。**

V1.1 不再把 Ceph RGW / 公有云对象存储作为产品标准交付基线。若客户已有其他 S3 服务，可通过 ObjectStoragePort 做项目级兼容，但不进入默认支持矩阵。MinIO / AIStor 的具体版本、镜像来源、授权和升级策略在 P0 锁定。

### 9.1 业务层唯一对象模型

业务模块只保存：

```text
file_id
tenant_id
bucket_alias
object_key
size
content_type
checksum（算法随 CryptoPort 套件）
status
created_at
```

业务模块不得保存：

- 存储实现的管理 API 对象；
- 具体节点地址；
- 临时 URL；
- AccessKey / SecretKey。

### 9.2 File Service

```text
FileService
   |
ObjectStoragePort
   |
S3 Adapter
   |
MinIO / AIStor
```

### 9.3 必须支持

- Upload；
- Multipart Upload；
- Download；
- Delete；
- Copy；
- Object Metadata；
- Presigned URL；
- Tenant Prefix；
- 文件大小限制；
- MIME 校验；
- Checksum；
- 生命周期策略引用。

### 9.4 租户边界

对象路径：

```text
/{env}/{tenant_id}/{business_type}/{yyyy}/{mm}/{uuid}
```

签名 URL 生成前必须重新校验 Tenant、Subject、Resource Permission、File Ownership / Reference。

## 10. 身份认证

Keycloak 负责：

- Credential；
- Login；
- OIDC；
- SAML；
- Federation；
- Session；
- MFA。

P2 自有：

- Person；
- Department；
- Position；
- Employment；
- Role；
- Permission；
- DataScope；
- FieldPolicy。

永久规则：

> Keycloak 的 Group / Organization / SCIM 只作为身份接入与 Provisioning 能力，不作为 NexusOne 企业组织主数据。

### 10.1 Keycloak 多租户模型

默认模型：**单 Realm + Organizations（每租户一个 Organization）**。

- 用户以手机号 / 邮箱为全局身份，一个自然人一个 Keycloak 用户；
- 租户成员关系的真相源是 P2 Employment，同步为 Organization 成员关系；
- 租户级 IdP（企业 SSO、LDAP/AD、域名发现）绑定到 Organization；
- 登录后选择或切换租户：服务端按 P2 Employment 校验成员关系后签发带租户上下文的会话，`tenant_id` 永不来自客户端自报；
- 独立 Realm 只作为 VIP / Regulated 交付等级的可选项，不作为默认模型；
- P0-3 验证 Organizations 在目标租户规模下的性能与 IdP 隔离。

### 10.2 会话模型

- 后端为无状态 Resource Server，不持有 HTTP Session；
- Web / H5 使用 OIDC Authorization Code + PKCE，Access Token 短期，Refresh 由 Keycloak 管理；
- 强制下线 = Keycloak 会话撤销 + 缓存黑名单加速；
- APP WebView / 小程序 web-view 沿用同一回跳契约，Token 不落宿主可读存储。

### 10.3 Keycloak 定制点

以下不是 Keycloak 原生能力，需要 Authenticator / Provider SPI 开发，排期按需求规格标注阶段：

- 短信验证码登录、短信 MFA（依赖短信服务商）；
- 扫码登录；
- 国密口令哈希（6.3）。

## 11. 权限引擎

权限引擎由平台自研，覆盖资源操作、数据范围、字段权限和搜索权限。首期不建设通用策略语言。

### 11.1 权限公式与合并语义

```text
求值顺序：
1. TenantBoundary                         不满足直接拒绝
2. Explicit Deny                          任一命中直接拒绝
3. ResourceActionGrant                    所有来源（用户 / 角色 / 岗位 / 部门 / 继承）的授权取并集，无授权则拒绝
4. DataScope                              同一 (resource, action) 下所有授权的 DataScope 取并集（OR），
                                          再 OR 上记录共享；结果编译为 SQL Predicate
5. FieldPolicy                            可见 / 编辑取并集；脱敏与敏感字段二次授权取最严格
6. ContextPolicy（有限条件）                 作为附加过滤，与上述结果取交
```

- 显式拒绝优先于其余允许策略；
- 引擎从 S0 起支持 Deny 语义，配置界面随需求规格阶段交付；
- 记录所有者（owner_id）是 DataScope 的固定维度，由台账系统字段提供。

### 11.2 Permission Engine

```text
PermissionEngine
├─ ResourcePermissionResolver
├─ RolePermissionResolver
├─ ExplicitDenyResolver
├─ DataScopeCompiler
├─ FieldPolicyCompiler
├─ ContextPolicyEvaluator
└─ PolicySnapshotManager
```

### 11.3 基础数据模型

```text

user_role
position_role
department_role
data_scope
field_policy
record_share
policy

```

`policy / policy_condition` 只承接需求规格已枚举的有限条件，不扩展为通用策略语言。

### 11.4 核心接口



### 11.5 禁止做成通用策略语言

条件能力只覆盖需求规格确定的：

- User；
- Role；
- Position；
- Department；
- Resource；
- Record Owner；
- 时间、IP 等有限 Context。

## 12. PolicySnapshot

P2 是权限真相源。策略变更通过数据库版本与本地失效通知下发。

- 策略版本按租户维护（`tenant_id, policy_version`）；
- Snapshot 按租户懒加载、LRU 淘汰，避免多租户 SaaS 全量驻留内存；
- 每个实例按短周期比对数据库中的租户策略版本，版本变化即重新加载；
- 缓存失效频道只用于加快失效，频道消息丢失不得使实例停留在旧快照；
- 服务启动可从数据库重建 Snapshot；
- 缓存故障不能导致权限数据丢失；
- 普通查询在版本落后时重新加载，超过时限仍无法加载则拒绝；
- 高风险写发现 Policy Version 过旧时 fail-closed。

拆成独立服务后，`PolicyDistributionPort` 可接入消息总线，领域模型保持不变。

## 13. Flowable

首期 Flowable 引擎与 NexusOne 应用同进程，**与业务库同库、独立 Schema（`flowable`）、共用 DataSource 与事务管理器**。业务保存和流程发起因此处于同一本地事务，不需要 JTA/XA。

```text
NexusOne P3
   |
WorkflowPort
   |
Flowable Engine（同进程）
   |
业务库 · flowable Schema（共用连接与事务）
```

约束：

- 不访问 Flowable 内部表；
- 不暴露 Flowable Admin API 给前端；
- P3 自己维护流程产品模型和业务引用；
- Flowable 只负责执行；
- Flowable 表由引擎自身脚本管理，不进入 Flyway；
- 独立 Flowable 进程留到故障域或容量证明需要之后，切换时改为 Outbox 发起并对账；
- 引擎替换仍视为独立项目。

P3 保存：

```text
workflow_definition_key
workflow_definition_version
workflow_instance_id
workflow_task_id
workflow_engine_type
```

## 18. 数据库与多租户隔离

V1.1 保持 Shared DB + Shared Schema + `tenant_id` 的产品模型，但把“SQL Runtime Guard”升级为 **结构化 Query AST / TableAccessPlan Guard**。

统一业务数据访问链：

```text
Domain Repository / Runtime Query
          |
          v
       Query AST
          |
          +-- TenantInjector
          +-- DataScopeInjector
          +-- SoftDeleteInjector
          +-- FieldPolicyProjector
          +-- Paging / Sort Validator
          |
          v
   TableAccessPlan Validator
          |
          v
      Dialect Renderer
      ├─ PostgreSQL
      └─ GaussDB
          |
          v
   Spring JdbcClient
          |
          v
       DataSource
```

### 18.1 第一道：Query AST 强制注入

P1–P5 业务查询必须首先形成结构化 Query AST。

Query AST 至少明确：

- 访问表集合；
- 表类型：tenant / platform；
- tenant_id 来源；
- DataScope Predicate；
- Soft Delete Predicate；
- Projection / FieldPolicy；
- Sort / Paging；
- Write Values。

所有 tenant table 查询和写入由 `TenantInjector` 强制加入 Tenant 条件，业务代码不能关闭。

### 18.2 第二道：TableAccessPlan Guard

运行时 Guard 不以“重新解析最终 SQL 文本”作为主要安全机制，而验证 Query AST 生成的 `TableAccessPlan`：

```text
TableAccessPlan
├─ tables
├─ table_scope
├─ tenant_required
├─ tenant_source
├─ data_scope_required
├─ write_columns
└─ platform_context
```

如果出现：

- tenant table 没有 Tenant Context；
- 写入 tenant_id 与上下文不一致；
- 未声明的跨租户访问；
- 非白名单 PlatformContext；
- 原生 SQL 未提供访问元数据；

则在进入 JdbcClient 之前直接拒绝并记录审计。

### 18.3 第三道：静态检查与契约测试

CI 强制禁止业务模块直接使用：

- `java.sql.Connection`；
- `JdbcTemplate`；
- `EntityManager nativeQuery`；
- MyBatis `${}`；
- 任意绕过 Nexus Repository / QueryExecutor 的 SQL 入口。

仅平台基础设施允许使用 `NativeSqlPort`。NativeSqlPort 调用必须显式提供 `TableAccessPlan` 并通过同一 Tenant Guard。

### 18.4 DDL 不走 Query AST

P3 动态 Schema 使用独立链路：

```text
Schema Metadata
      |
      v
   Schema AST
      |
Schema Validator
      |
Dialect Renderer
├─ PostgreSQL
└─ GaussDB
      |
      v
   DDL Executor
```

动态新表必须登记到 `table_registry`：

```text
table_name
scope = tenant | platform | app_shared
tenant_required
schema_version
owner_module
```

### 18.5 平台 scope 与跨租户访问

平台自己的管理数据使用 `platform` scope。

跨租户访问只有平台白名单路径允许，例如：

- 平台运营汇总；
- 对账；
- 审计治理；
- 明确授权的集团汇总。

进入 PlatformContext 必须：

- 由服务端产生；
- 有调用原因；
- 有 Actor；
- 有 Trace ID；
- 写入审计。

### 18.6 数据库账号

- NexusOne 业务库使用最小权限账号；
- Keycloak、Flowable 使用独立 Schema / 独立权限；
- 不允许业务模块直接访问 Keycloak / Flowable 内部表；
- PostgreSQL RLS 可以作为特定部署的额外 defense-in-depth，但不属于跨数据库统一产品语义。

### 18.7 后期交付等级

S2 以后允许按客户交付要求提供 Dedicated DB / Dedicated Cluster，但不产生第二套业务模型。

### 18.8 强制规则

- 所有 tenant table：`tenant_id NOT NULL`；
- 所有业务查询：Query AST；
- 所有原生 SQL：NativeSqlPort + TableAccessPlan；
- 所有后台执行：显式 Tenant Context；
- Redis Key：带 Tenant；
- MinIO / AIStor Object Prefix：带 Tenant；
- 导出、报表、Webhook、Task Queue、Outbox：带 Tenant；
- 隔离失败属于发布阻断级缺陷。

## 19. P3 台账数据引擎

### 19.1 存储模型

> **每个台账一张物理表。** 不使用 EAV，不使用 JSONB 宽表承载主字段。

| 台账来源 | 物理表 | 归属 | 跨租户共享 |
|---|---|---|---|
| 租户自建台账 | `l_{tenant_code}_{ledger_code}` | 单租户 | 否 |
| 应用包（P4）台账 | `a_{app_code}_{ledger_code}` | 平台 | **是**，所有安装该应用的租户共用一张表，以 `tenant_id` 区分 |

业务预期是：

- 租户自建台账数量受 Quota 控制；
- 大部分标准业务通过发布应用交付；
- 因此租户规模增长不应线性增加应用包物理表数量。

### 19.2 系统字段

每张台账表固定包含：

```text
id
tenant_id
created_at
created_by
updated_at
updated_by
deleted_at
version
schema_version
ext_data
```

`schema_version` 表示记录写入时的台账结构版本。

`ext_data` 仅用于应用包共享表的租户覆盖字段，不承载核心模型字段。

### 19.3 DDL 治理

- P3 SchemaService 负责动态表和字段；
- Flyway 只管理平台静态 Schema，不管理台账表；
- 动态 DDL 必须经过 Schema AST + Dialect Renderer；
- 新建物理表必须登记 `table_registry`；
- `SchemaDriftCheck` 分批检查元数据和物理 Schema；
- 应用包共享表的 ADD COLUMN 属于平台级 Schema 演进；
- 租户扩展字段默认进入 `ext_data`；是否建立索引受租户配额和平台索引上限约束。

### 19.4 查询编译

台账 CRUD、列表、搜索、报表的数据访问必须使用第 18 节 Query AST。

典型链路：

```text
Ledger Metadata
      |
Runtime Query Model
      |
Query AST
      |
Tenant + DataScope + SoftDelete
      |
Dialect Renderer
      |
JdbcClient
```

### 19.5 容量与台账配额

V1.1 正式增加 `custom_ledger_quota`。

PoC 后必须冻结：

- 单租户最大自建台账数；
- 单应用最大共享台账数；
- 单集群最大动态物理表数；
- 单库最大索引数量；
- 单台账最大行数；
- 单租户最大可索引扩展字段数；
- SchemaDriftCheck 单批扫描数量；
- 动态 DDL P95；
- 系统 Catalog 查询性能。

达到任意阈值后：

- 禁止继续创建租户自建台账；或
- 进入 Dedicated DB / 分片 / 迁出评估。

### 19.6 应用包共享表的 Forward-Compatible Schema

应用包共享物理表存在“不同租户运行不同应用版本”的场景，因此 Schema 演进必须采用：

```text
Expand
  ↓
Migrate
  ↓
Switch
  ↓
Contract
```

强制规则：

1. 应用升级不得删除已有业务数据；
2. 在线升级不得立即 DROP COLUMN；
3. 在线升级不得直接做不可兼容的数据类型收窄；
4. 字段改名采用“新增字段 → 回填 → 双读/兼容 → 延迟废弃”；
5. 数据迁移必须幂等；
6. 不可逆转换必须保留原字段或提供补偿数据；
7. 单租户应用回滚只回滚：
   - 配置；
   - 表单/页面；
   - 流程定义；
   - 规则；
   - 运行版本；
8. **单租户回滚不得回滚共享物理 Schema，不得删除或回滚已有业务数据**；
9. 只有所有受支持租户版本均不再依赖旧结构并经过保留期后，才允许 Contract 物理清理。

V1.1 不建设“单租户逻辑恢复工具”。租户导出/导入只属于迁移能力，不属于灾备恢复。

## 20. 表达式与沙箱

公式字段、动态默认值、规则条件、办理人表达式、决策表输入共用一套受限表达式语言（候选 Aviator / SpEL 受限模式，P0 锁定）。

规则：

- 只暴露白名单函数（数学、字符串、日期、集合、当前用户 / 组织上下文）；
- 禁止反射、类加载、IO、线程、系统属性访问；
- 单次求值有 CPU 时间与内存上限，超限中止并记录；
- 表达式在发布时静态校验并缓存编译结果；
- 不提供租户任意 JavaScript / Groovy 脚本。

## 21. 组件"触发式引入"规则

| 组件 | 首期状态 | 引入触发条件 |
|---|---|---|
| Kafka | 后置 | Outbox 吞吐、Replay、Consumer Group、多服务事件规模达到瓶颈 |
| Apicurio | 后置 | Event Schema 数量和团队规模使 Git Schema 治理不可控 |
| OpenSearch | 后置 | 数据库搜索性能或全文检索功能不足 |
| APISIX | 后置 | P5 API 产品化、动态路由和客户端流量治理成熟 |
| OpenBao / KMS | 后置 | 大量租户 Secret、密钥轮换、集中 Secret 审计；国密 KMS 按客户要求 |
| Kubernetes | 后置 / 非必需 | SaaS 规模、弹性、自动调度明确证明其运维收益高于成本 |
| 独立微服务 | 后置 | 单模块扩展、团队边界或故障域需要独立部署 |
| 台账分区 / 迁出 | 后置 | 单表行数或单租户数据量达到 PoC 设定阈值 |

任何新组件必须回答：

1. 解决哪个已经发生的问题？
2. 不引入会有什么量化损失？
3. 增加多少部署与运维成本？
4. 独立部署客户（含 GaussDB-only / 信创）是否也必须安装？

## 22. 数据库边界

模块化单体不等于数据库无边界。

逻辑数据边界：

```text

P2 iam
P3 business_meta
P3 business_data（台账物理表）
P4 market
P5 integration

```

禁止：

- 模块绕过 Service/Repository 直接查询其他产品的私有表；
- 跨产品业务 SQL JOIN 形成隐式耦合；
- P3 查询 Keycloak / Flowable 内部表。

Keycloak 使用独立私有库（或同实例独立数据库）；Flowable 使用业务库独立 Schema（第 13 节）。

## 34. 最终技术原则

1. **模块化单体优先，微服务按事实拆分。**
2. **首期组件越少越好。**
3. **核心领域模型必须属于 NexusOne。**
4. **第三方只提供成熟执行能力。**
5. **缓存是缓存，不是业务数据库；关键幂等键落库。**
6. **默认产品固定 Redis 与 MinIO / AIStor；业务层分别只认 Redis Protocol 与 S3 API。**
7. **权限核心自研，DataScope / FieldPolicy 是核心能力。**
8. **三条执行通道：Quartz、Task Queue、Outbox。**
9. **租户隔离由应用层三道防线强制，不依赖数据库 RLS。**
10. **每个台账一张物理表；租户自建台账受 Quota 控制，应用包台账跨租户共享。**
11. **应用包共享 Schema 只允许 Forward-Compatible 演进；租户版本回滚不得回滚共享物理 Schema 或已有业务数据。**
11. **GaussDB-only 与信创组合是一等交付目标，不允许额外要求 PostgreSQL。**
12. **密码学经 CryptoPort，国际 / 国密双套件。**
13. **Kafka、OpenSearch、API Gateway、Secret Platform 都必须达到触发条件才引入。**
14. **P2 不成为每次查询的远程授权单点。**
15. **即使没有 MQ，也必须有 Outbox、幂等和 Reconciliation。**
16. **SaaS 与独立部署尽可能共用同一代码和组件。**
17. **AI 完全不属于本项目。**

## 35. 基准决策

- 首期采用模块化单体，按产品模块保持代码与数据边界；
- Spring Boot 只使用稳定 GA 版本，P0 锁定 minor；
- 默认缓存固定为 Redis；对象存储固定为 MinIO / AIStor；业务代码分别只依赖 Redis Protocol 与 S3 API；
- 租户隔离：共享库 + 共享 Schema + tenant_id + 应用层三道防线，不使用 RLS；
- P3 每个台账一张物理表，租户自建表以 tenant_code 唯一标识，应用包台账跨租户共享；
- Flowable 首期同进程、同库独立 Schema、共用事务；
- Keycloak 单 Realm + Organizations；
- Keycloak / Flowable / Quartz / Flyway 正式纳入国产化支持矩阵；P0 锁定具体版本组合并完成 GaussDB-only 验收；
- 信创组合、等保三级技术项、商用密码双套件进入 P0 与验收门禁；
- 部署采用 Linux + Docker Compose 或 systemd；
- 三条执行通道：Quartz、Task Queue、Outbox；
- 权限引擎为自研 Nexus Permission Engine；
- Kafka、OpenSearch、APISIX、Apicurio、OpenBao、Kubernetes 按触发条件后置；
- PostgreSQL / GaussDB 双数据库支持；
- SaaS 与独立部署使用同一产品代码基线。

## 36. 结论

技术路线：

> **业务平台先行，基础设施按需演进。**

第一阶段真正需要长期掌握的是：

```text
Tenant / Tenant Relation
Identity / Org / Position
Permission / DataScope / FieldPolicy
App / Schema / Ledger（物理表引擎）
Form / Workflow / Rule / Expression
Package / SKU / Subscription
API / Webhook / Connector
```

真正需要首期部署的外部基础组件控制在：

```text
Database（PostgreSQL / GaussDB）
Redis
MinIO / AIStor
Keycloak
Flowable（进程内）
```

其余能力优先由 Spring Boot、数据库、缓存、Quartz / Task Queue 和自有模块完成。

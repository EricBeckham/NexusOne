## 1. 备份范围

| # | 对象 | 内容 | 是否必须 | 方式 |
|---|---|---|---|---|
| 1 | **Postgres 产品库**（`NEXUS_DB_URL` 指向的那一个库） | 10 个 schema：`platform`（含 `flyway_schema_history`、`secret_ciphertext`、审计链）、`iam`、`market`、`business_meta`、`business_data`（运行时创建的租户台账物理表）、`files`（元数据）、`notify`、`integration`、`flowable`（引擎自有）、`quartz` | **必须** | `pg_dump -Fc` 整库导出，一份就能覆盖全部 schema |
| 2 | **对象存储桶**（`S3_TEST_BUCKET`，默认 `nexus-files`） | 上传文件的字节；启用冷归档后还包括审计冷归档对象 | 使用 S3/MinIO 时**必须** | `mc mirror` |
| 3 | **`NEXUS_CRYPTO_MASTER_KEY`**，以及 `NEXUS_CRYPTO_KEY_ID`、`NEXUS_CRYPTO_KEY_VERSION`、`NEXUS_CRYPTO_SUITE` | 解密 `platform.secret_ciphertext`（IdP client secret、P5 Credential） | **必须**，而且要**与库备份分开保管** | 运维保管库；**不和 dump 放在同一处** |
| 4 | 部署配置（不含密钥的环境变量）和**应用版本（git SHA）** | 恢复时要用相同或更新的版本启动（Flyway 只能向前迁移，`outOfOrder` 保持关闭） | 必须 | 部署记录 |
| 5 | Keycloak（`NEXUS_IAM_IDP=keycloak` 时） | 外部 IdP 的 realm、用户、客户端 | 由 IdP 自己负责 | 按 Keycloak 官方 realm 导出 / 数据库备份做 |
| — | Redis | 只是缓存 / 锁，可以重建 | **不备份** | — |

> ⚠️ **只有 #1、没有 #3 = 所有托管密钥永久不可恢复。** 如果运行时是 `NEXUS_CRYPTO_KEY_SOURCE=ephemeral`（默认），根本不存在可以备份的主密钥，重启后密文就读不出来，**备份也救不回来**。所以上线前必须先切到 `env`（见 L12）。

## 2. 一致性说明

- `pg_dump` 本身给出的是库内一致的快照。库和对象存储之间**没有**原子一致性。
- 顺序：**先导出库，再镜像对象**。这样库里引用的对象一定存在于对象备份中，除非对象在两步之间被删除。对象备份里可能多出孤儿对象，这不影响恢复。恢复后可以用文件对账（G10 reconcile preview）检查。
- 演示 / 内测环境最好在低峰期操作，或短暂停写。

## 3. 备份步骤

```bash
export PGHOST=<db-host> PGPORT=<db-port> PGUSER=<backup-role> PGDATABASE=<product-db>
# 口令通过 ~/.pgpass 或 PGPASSWORD 注入，不要写进命令历史
ts=$(date -u +%Y%m%dT%H%M%SZ)
pg_dump --format=custom --file=nexusone-$ts.dump
sha256sum nexusone-$ts.dump > nexusone-$ts.dump.sha256
```

```bash
mc alias set nexus <s3-endpoint> "$S3_ACCESS_KEY" "$S3_SECRET_KEY"
mc mirror --overwrite nexus/<bucket> ./objects-$ts/<bucket>
```

然后记录下面这些信息：备份时间、应用 git SHA、`SELECT max(installed_rank), max(version) FROM platform.flyway_schema_history WHERE success`、dump 的 sha256、对象数量，以及**使用的主密钥标识**（`key-id` / `key-version`，**不要记录主密钥本身**）。

保留策略建议（演示 / 内测）：每天 1 份，保留 7 天；每周 1 份，保留 4 周。dump 要放在加密存储里，访问权限与生产数据相同。

## 4. 恢复步骤

1. **准备一个空库**，库名不要和线上重名：
   ```bash
   psql -d postgres -c "CREATE DATABASE nexusone_restore TEMPLATE template0 ENCODING 'UTF8';"
   ```
2. **校验并导入**：
   ```bash
   sha256sum -c nexusone-<ts>.dump.sha256
   pg_restore --dbname=nexusone_restore --exit-on-error --no-owner nexusone-<ts>.dump
   ```
3. **恢复对象**，可以先恢复到隔离的前缀里核对：
   ```bash
   mc mirror --overwrite ./objects-<ts>/<bucket> nexus/<bucket>
   ```
4. **配置密钥**：`NEXUS_CRYPTO_KEY_SOURCE=env`，`NEXUS_CRYPTO_MASTER_KEY`、`KEY_ID`、`KEY_VERSION`、`SUITE` 都要和备份时**完全一致**。
5. **启动前先关掉会动数据的定时任务**，确认恢复结果之后再打开：
   - `NEXUS_AUDIT_HOT_PURGE_SCHEDULE_ENABLED=false`、`NEXUS_AUDIT_ARCHIVE_SCHEDULE_ENABLED=false`、`NEXUS_AUDIT_COLD_ARCHIVE_SCHEDULE_ENABLED=false`
   - 注意：dump 里处于 PENDING 状态的 outbox 消息，会在启动后由 dispatcher 投递（通知可能重发，消费端有幂等保护，见 G3）。dispatcher 目前**没有**环境变量开关。
6. **启动应用**，使用与备份时相同或更新的版本，`NEXUS_DB_URL` 指向恢复库。Flyway 会校验历史，只有新版本才会继续迁移。Flowable 引擎会复用已恢复的 `flowable` schema。

## 5. 恢复后验证清单

| # | 检查 | 期望结果 |
|---|---|---|
| 1 | `GET /actuator/health` | `UP` |
| 2 | `platform.flyway_schema_history` 最高版本 | 等于备份时记录的版本（新版本启动时可以更高） |
| 3 | 各 schema 关键表行数（租户、账号、安装、申请、流程实例、审计记录） | 与备份前的记录一致 |
| 4 | 审计哈希链校验 `GET /api/v1/audit/chain`（平台审计管理员） | `intact=true` |
| 5 | 对一个已配置、且备份前测试连接成功过的 IdP，执行「测试连接」 | `SUCCEEDED` → **证明主密钥正确**。注意：密钥状态只读元数据，不做解密，所以即使主密钥错了也会显示 configured；主密钥错时测试连接返回 `FAILED`（服务层有意吞掉底层异常，也不写日志）。如果 IdP 本身可达、却返回 `FAILED`，首先怀疑主密钥 / key-id 配置 |
| 6 | 随机下载 1–2 个已上传文件 | 字节与原文件一致 |
| 7 | 用演示路径抽查：「我的申请」和待办列表 | 数据可见，租户隔离正常 |
| 8 | 核对完成后，按原配置重新打开归档 / 清理定时任务 | — |

## 6. 演练方式（非生产）

- 流程演练：用 `scripts/g6-recovery/run-drill.sh`（专用集群，端口 55432，拒绝 5432 和敏感库名）；单租户逻辑恢复用 `run-single-tenant.sh`。这两个脚本用的是**合成种子**，证明的是流程本身。
- 专用库演练：P7 已完成 PostgreSQL 主链路并记录[证据](./P7_备份恢复演练证据.md)。
- 产品库演练：在一个演示环境跑一遍 §3 → §4 → §5，并把耗时（作为 RTO 参考）、dump 大小、验证结果写回本文。P7 的合成库结果不能替代这一步。

## 7. 边界与已知限制

- **RPO**：按天备份时最多丢一天的数据；没有 WAL 归档 / PITR。**RTO**：取决于库的大小，首次演练后填写。
- 没有主密钥轮换 / 重新加密工具。更换主密钥就意味着所有托管密钥要重新录入。
- 单租户恢复不是产品能力，只在演练脚本层面做过验证。`RecoveryPort` 仍然只是 dry-run。

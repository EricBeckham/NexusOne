# PL · 平台级与租户级功能重新规划 V0.1

基线 `main@ed5173d9`。本文是规划与决策稿，不代表已实现、已部署或已验收。

## 0. 一句话

**平台是一个特殊租户**：平台级与租户级共用同一套「组织—人员—岗位—角色—台账—表单—流程」模型，用作用域（平台 / 租户）区分；平台在此之上多一层「应用与产品」的定义、分类、上架能力，租户订购后得到应用实例，可**直接复用**或**派生个性化**；租户门户的菜单由「应用中的台账表单」生成，成员按「岗位 → 角色」自动看到自己能用的菜单。

## 1. 概念模型

### 1.1 两级用户

| | 平台级 | 租户级 |
|---|---|---|
| 所在租户 | 平台租户（`…0001`） | 各业务租户 |
| 管理对象 | 租户（开户、启停、关系、权益配额、注册审核）、应用与产品 | 本租户的组织、人员、应用实例、门户 |
| 典型身份 | 平台运营（系统管理员职责）、平台安全 / 审计管理员 | 租户管理员、一般用户 |

平台管理租户：租户的创建、启停、上下级、订购与权益都在平台侧可见可管；租户不能看到其他租户。

### 1.2 组织、人员、岗位、角色（两级同构）

```
人员 ──任职──▶ 岗位 ──绑定──▶ 角色 ──授权──▶ 资源:动作（台账 / 表单 / 流程 / 菜单）
  └─ 属于 ─▶ 部门（组织架构）
```

- **组织架构**：部门树。
- **岗位**：可绑定一个或多个**本级**角色（平台岗位只能绑平台角色，租户岗位只能绑租户角色）。
- **人员**：通过任职绑定岗位（一个主职 + 若干兼职），不直接挂角色（保留「直接授予」作为例外通道，默认不用）。
- **角色**：一组授权（资源 + 动作 + 数据范围）。平台角色 = 平台职责与平台功能授权；租户角色 = 租户内业务授权。

一个人的有效权限 = 其所有 ACTIVE 任职岗位绑定的角色的授权并集（再叠加数据范围与显式拒绝）。

### 1.3 台账、表单、流程

- **台账**：数据结构（字段、类型、必填、索引），落为物理表。
- **表单**：台账的可视化呈现（布局、控件、校验、只读 / 可编辑字段）。一张台账可有多个表单（填报表单、审批表单、查看表单）。
- **流程**：基于**角色**的流转——每个节点指派到角色（或岗位），运行时解析为当前租户中持有该角色的人员。

### 1.4 应用、产品、分类

| 概念 | 定义 | 例 |
|---|---|---|
| **应用** | 一个完整业务功能：若干台账 + 表单 + 流程 + 角色包（该应用需要的角色与默认授权）+ 功能入口，**有版本** | 请假、报销 |
| **应用分类** | 应用的归类，用于市场展示与门户分组 | OA、全过程 |
| **产品** | 一个或多个应用的组合，是**上架与订购的单位**，挂 SKU 与权益 | 「OA 基础包」= 请假 + 报销 |
| **上架** | 产品的某个版本组合对租户可见、可订购 | |

### 1.5 平台模板与租户实例（复用 / 个性化）

租户订购产品后，产品内每个应用在租户侧形成**应用实例**，每个实例二选一：

| 模式 | 含义 | 平台升级时 |
|---|---|---|
| **复用（引用）** | 直接使用平台发布的台账 / 表单 / 流程 / 角色包版本 | 平台发布新版本后，租户可一键升级（或按策略自动） |
| **个性化（派生）** | 以某平台版本为**基线**复制一份租户副本，租户可改表单、流程、角色，可加台账字段 | 不自动变；提供「基线差异」查看与手动合并 |

解析顺序：**租户个性化 > 平台版本**。个性化粒度按对象（表单 / 流程 / 角色可各自派生），不强制整应用派生。

### 1.6 租户门户

- **每个台账表单就是一个功能入口**（菜单项）。应用实例安装后，其功能入口进入租户的「可用功能」池。
- 租户管理员配置：**门户首页模块**（待办、我的申请、通知、快捷入口、统计卡片等）与**功能菜单结构**（分组、排序、显隐、名称）。
- 成员看到的菜单 = 租户菜单结构 ∩ 该成员经「岗位 → 角色」对功能入口有 `read` 权限的项；无权的入口不显示（服务端仍拒绝越权访问）。

## 2. 现状对照

| 领域 | 已有（可复用） | 缺口 |
|---|---|---|
| 平台 / 租户两级 | 平台即租户 `…0001`（P1）；平台三权职责（系统 / 安全 / 审计）；AUTH6 平台只读桥；PV 按身份显示产品 | 平台级与租户级在界面上未显式区分作用域 |
| 组织 / 人员 / 岗位 | P2 部门、人员、岗位、任职（主职 / 兼职），按租户隔离，平台租户同构 | 平台侧组织管理入口按平台作用域组织 |
| 岗位绑定角色 | 权限引擎已支持 `position` 作为授权主体（`roleCodesFor` 按岗位解析角色） | **没有「岗位 ↔ 角色」绑定的管理界面**；当前靠个人直接指派（如 `tenant_member` 种子挂给每个人） |
| 角色 | 角色、授权矩阵、数据范围、字段策略、三权互斥 | 角色未与「应用角色包」关联；租户角色来源混杂（种子 / 手工） |
| 台账 / 表单 | P3 租户台账与表单；P1 平台表单模板（仅表单模板，未绑定台账） | **平台级台账**缺失；平台表单模板与租户台账无「派生」关系 |
| 流程 | P3 流程设计、发布；节点指派支持 `PERSON / POSITION / ROLE`；平台默认流程 + 安装级租户覆盖（`InstallationProcessConfiguration`） | 流程默认按人指派的示例多；覆盖只针对流程，未扩展到表单 / 角色；无基线差异 |
| 应用 / 产品 | P4 `AppPackage` + `AppVersion`（审批 / 发布）+ `Sku`（一个 SKU 对应一个应用）+ `ProductDefinition`（**一个**表单模板 + 一个流程 + 默认权限包）+ 目录、订阅、安装、开通申请 | **应用无分类**；**产品不能组合多个应用**；应用只能含一张表单；「应用」与「产品定义」概念交错 |
| 订购 | 订阅、开通申请（平台审核）、安装、权益投影、配额 | 订购后未按应用角色包落租户角色；门户不随安装生成入口 |
| 租户门户 | 静态导航（`web/src/nav/*.js`）；PV 产品级可见性 | **无门户配置**；菜单不来自台账表单；未按角色过滤功能菜单 |
| 其他 | 办结后动作（FA）；审批通知仅在表单路径发送 | 产品申请路径缺站内通知（见此前定位） |

## 3. 目标模块分工

| 产品 | 平台级职责 | 租户级职责 |
|---|---|---|
| **P1 星域** | 租户管理（开户、启停、关系、权益配额、注册审核）、平台服务态、平台审计 | — |
| **P2 星权** | 平台组织 / 人员 / 岗位 / 角色（平台作用域） | 租户组织 / 人员 / 岗位 / 角色；岗位绑定角色 |
| **P3 星构** | 平台台账 / 表单 / 流程 / 角色包的设计与版本 | 租户个性化（派生、编辑、基线差异）；门户配置；业务运行（工作台） |
| **P4 星市** | 应用（含分类、版本）、产品（应用组合）、SKU、上架、开通审核 | 浏览目录、订购产品、管理已订购应用实例（复用 / 个性化、升级） |
| **P5 星联** | 开放接口目录 | 租户接口凭证（按权益） |

## 4. 数据模型调整（草案，需迁移卡单独评审）

| 变更 | 说明 |
|---|---|
| `app_category`（新） + `app_package.category_code` | 应用分类，平台维护 |
| `app_version` 内容扩展为「应用清单」 | 版本包含：台账定义列表、表单列表、流程列表、角色包、功能入口列表（替代「一个产品定义 = 一个表单模板 + 一个流程」） |
| `product`（新）+ `product_app`（新） | 产品 = 多个应用版本的组合；SKU 改挂产品 |
| 平台台账 / 表单 / 流程 / 角色包「模板」 | 平台作用域的设计对象，发布为不可变版本，被应用版本引用 |
| `tenant_app_instance`（新） | 租户侧每个已订购应用：`mode = INHERIT / FORK`、`base_version`、状态 |
| `tenant_override`（新，按对象） | 个性化对象（表单 / 流程 / 角色）指向平台基线版本 |
| `position_role`（沿用权限授权主体 `position`） | 以「岗位」为主体的角色指派，提供管理界面，不新造表 |
| `portal_menu` / `portal_home_module`（新） | 租户门户菜单结构与首页模块配置；菜单项引用应用实例的功能入口 |
| `function_entry`（随应用版本） | 功能入口 = 台账 + 表单 + 默认动作；授权资源键稳定，便于菜单按角色过滤 |

现有 `ProductDefinition` / `InstallationProductPin` / `InstallationProcessConfiguration` 作为过渡：迁移时映射为「单应用产品」与「流程对象的租户覆盖」。

## 5. 分期路线

| 波次 | 目标 | 主要内容 | 演示结果 |
|---|---|---|---|
| **PL1 组织与角色** | 两级同构、岗位驱动授权 | 平台 / 租户作用域标识；**岗位绑定角色**管理界面（平台岗位 ↔ 平台角色、租户岗位 ↔ 租户角色）；人员任职岗位；有效权限预览；逐步替代「给每人挂 `tenant_member`」 | 改岗位角色后，成员权限随之变化 |
| **PL2 应用模型** | 应用 = 多台账表单 + 流程 + 角色包，可分类 | 应用分类；平台台账 / 表单 / 流程 / 角色包设计与版本；应用版本清单；流程节点默认按角色指派 | 平台建「请假」「报销」两个应用，归入 OA |
| **PL3 产品与上架** | 产品 = 应用组合 | 产品、产品—应用关系、SKU 挂产品、上架 / 下架；开通审核沿用 | 「OA 基础包」= 请假 + 报销 上架 |
| **PL4 订购与实例化** | 订购即可用 | 订购产品 → 生成应用实例（复用模式）→ 按角色包创建租户角色与默认授权 → 功能入口进入可用池；审批通知补齐 | 租户订购后直接可发起请假 |
| **PL5 个性化** | 复用或派生 | 对表单 / 流程 / 角色派生租户副本；基线差异；平台升级提示与手动合并 | 租户改报销表单加一个字段，不影响平台版本 |
| **PL6 租户门户** | 菜单来自台账表单、按角色显示 | 门户菜单结构与首页模块配置；成员菜单 = 菜单 ∩ 角色 `read`；与 PV 产品可见性合并为「产品 → 功能」两层 | 周然只看到请假 / 报销入口；林晓多看到配置入口 |
| **PL7 迁移与验收** | 旧数据平滑过渡 | 现有产品定义、安装、流程覆盖迁移为新模型；DEMO-U 三人路径改写 | 三人演示走新模型 |

每波按既有纪律拆卡：文档 / 迁移 / 后端 / 前端 / 验收分开；迁移只放迁移；一卡一 PR。

## 6. 待决策

1. **应用与产品的边界**：是否允许「单应用即产品」自动生成（推荐：允许，上架时自动包一层产品）？
2. **个性化粒度**：按对象派生（表单 / 流程 / 角色各自）还是整应用派生（推荐：按对象）？
3. **平台升级策略**：复用模式的租户是自动升级、提示后手动升级，还是按产品设定（推荐：提示后手动，支持产品级「自动小版本」开关）？
4. **角色包落地**：订购时自动创建租户角色并**绑定到哪些岗位**——默认不绑定、由租户管理员绑定（推荐），还是按岗位编码约定自动绑定？
5. **直接给人授权**：保留为例外通道还是禁止（推荐：保留，界面上标注「例外授权」并可审计）？
6. **门户与产品切换器**：门户菜单是否替代现在的五产品切换（推荐：租户成员只见门户；平台 / 租户管理员保留产品切换进入配置类功能）？
7. **平台台账是否物理建表**：平台台账作为模板不落物理表，只在租户实例化时建表（推荐）？

## 7. 与已完成工作的关系

- **PV（产品可见性）**：保留为「产品层」过滤；PL6 在其下增加「功能层」菜单过滤。
- **PV4 / FA3**：`tenant_process_designer` 等设计者角色，PL1 后改由岗位绑定获得。
- **AUTH6 平台只读桥**：平台级功能的访问方式不变。
- **FA 办结后动作**：属于应用内流程能力，进入应用版本清单（PL2），个性化时可随流程派生。
- **审批站内通知缺口**：并入 PL4（订购即可用的完整审批体验）。
